# День 19. Композиция MCP-инструментов

На одном MCP-сервере три инструмента выстроены в пайплайн: `search` находит заметки, `summarize` обрабатывает их, `save_to_file` сохраняет сводку. Клиент тот же, что в днях 16–18: соединение по stdio, `list_tools`, перевод схем, вызов `Client.call_tool`. Сервер свой, запускается тем же интерпретатором: `sys.executable day19/server.py`. Источник данных локальный — небольшой корпус заметок в `day19/corpus/`. Внешний API и лимиты не нужны, прогоны детерминированные.

Цепочка выполняется автоматически оркестратором (`pipeline.py`). Он вызывает инструменты только через MCP, не через функции Python в обход. Если шаг вернул пусто или ошибку, следующий инструмент не вызывается, фиксируются шаг остановки и причина. Диспетчер агента повторяет то же правило, если модель пытается продолжить цепочку сама. В ответе при сбое нет выдуманной сводки и нет «сохранённого» файла: либо модель честно описывает остановку, либо её ответ заменяется каноническим сообщением.

Сценарии сбоя переключаются надёжно, а не «по настроению» модели. Запрос с маркером «пустой поиск» или `__empty__` всегда даёт пустой `search`. Запрос с маркером «сломанный источник» или `__fail__` возвращает документ с токеном `<<<FAIL_SUMMARIZE>>>`, на котором `summarize` возвращает ошибку.

## Инструменты и остановка

Три инструмента регистрируются декоратором `@server.tool`. Параметры — аннотации типов и `pydantic.Field(description=...)`. Из них SDK собирает JSON Schema, которую клиент получает в `tools/list`.

| Инструмент | Параметры | Что делает |
| --- | --- | --- |
| `search` | обязательный `query` | Ищет в локальном корпусе и возвращает список документов: id, title, text. Ничего не суммирует и не сохраняет. |
| `summarize` | обязательный `documents` (JSON-список из `search`) | Строит краткую сводку по найденным заметкам. Пустой вход или сломанный источник — ошибка, сводки нет. |
| `save_to_file` | обязательный `text`, необязательный `filename` | Сохраняет текст сводки в папку `out/` внутри `day19`. Пустой текст не пишется. |

Файлы из `out/` в git не попадают. Путь задаётся переменной `PIPELINE_OUT`.

Порядок жёсткий: `search` → `summarize` → `save_to_file`. В `summarize` уходят именно `hits` из поиска, в `save_to_file` — поле `summary` из второго шага. Пустой поиск останавливает цепочку на `search`: `summarize` и `save_to_file` не вызываются. Ошибка `summarize` останавливает цепочку на втором шаге: `save_to_file` не вызывается. В обоих случаях итогового результата нет, шаг и причина видны в ответе.

## Как запустить

Нужны Python 3 и пакет `mcp`. Внешний API для сервера не нужен, ключ модели — только для агента и прогона:

```powershell
pip install -U "mcp>=2"
# или: pip install -r day19/requirements.txt
```

Ключ — в окружении `DEEPSEEK_API_KEY` или в `day02/.env` / `day19/.env`. Проверка без модели:

```powershell
cd day19
python -m unittest test_pipeline.py
```

Три живых сценария и свободный запрос:

```powershell
python check_pipeline.py
python agent.py Найди заметки про MCP и память агента, сделай сводку и сохрани в файл pipeline-success.md
```

На странице http://127.0.0.1:8765/ день 19 поднимает тот же сервер и умеет прогнать успешную цепочку и оба сбоя кнопками. Если пакета `mcp` нет, страница не падает, а показывает, чего не хватает. Сервер стартует тем же `python`, которым запущена страница.

Часть подменяет `call_tool` и проверяет, что оркестратор передаёт документы из `search` в `summarize`, а сводку — в `save_to_file`, и что после пустого первого шага или ошибки второго следующие инструменты не вызываются. Живые тесты поднимают сервер по stdio: успешная цепочка пишет файл, оба сбоя оставляют папку пустой и фиксируют шаг с причиной. ## Ограничения

Корпус учебный и небольшой, поиск — простое пересечение слов, без ранжирования по смыслу. Из-за этого широкий запрос может задеть соседние заметки, как в успешном прогоне: кроме MCP и памяти в сводку попали планировщик и описание пайплайна. Для задания этого достаточно, на настоящий поисковый движок это не претендует.

`summarize` собирает сводку детерминированно (заголовок и первое предложение), а не вызывает отдельную модель. Так проще проверить передачу данных и не упереться в лимиты. Сломанный источник и пустой поиск включены маркерами в запросе, чтобы тесты и демо всегда могли их показать.

Планировщика здесь нет: цепочка запускается запросом агента, кнопкой на странице или скриптом проверки. Папка `out/` живёт, пока жив процесс и пока её не очистили.

Модель описывает уже выполненный пайплайн и теоретически могла бы выдать сводку, которой нет. В этом прогоне она этого не сделала; на такой случай в коде есть замена ответа каноническим сообщением об остановке.
