# День 16. Подключение MCP

Агент дня 6 ходит в модель тем же циклом: запрос, вызов инструмента, возврат результата, снова запрос. К этому циклу подключён готовый MCP-сервер `@modelcontextprotocol/server-filesystem` (версия сервера в прогоне — 2.4.0, имя `secure-filesystem-server`). Клиент — пакет Python `mcp`. Соединение идёт по stdio: код запускает `npx -y @modelcontextprotocol/server-filesystem <песочница>` и забирает список инструментов. Песочница — папка `day16/sandbox`.

Локальные инструменты дня 6 остались своими функциями: `get_current_time`, `calculate`, `convert_usd_to_rub`. Инструменты MCP мы не писали: их схемы приходят с сервера, а вызов идёт через `Client.call_tool`.

## Как запустить

Нужны Python 3 и пакет клиента, плюс Node.js, потому что готовый сервер запускается через `npx`.

```powershell
pip install mcp
# или: pip install -r day16/requirements.txt
```

Node.js LTS — с https://nodejs.org/. После установки в том же терминале должны работать:

```powershell
python --version
npx -v
```

На Windows команда называется `npx.cmd`; код ищет её сам. Первый запуск скачивает пакет сервера в кэш npm, для этого нужен интернет:

```powershell
npx -y @modelcontextprotocol/server-filesystem day16\sandbox
```

Дальше сервер поднимает сам агент. Примеры:

```powershell
cd day16
python agent.py Какие файлы есть в песочнице и что в notes.txt?
python agent.py --mixed Прочитай order.txt и посчитай итог заказа
```

Флаг `--mixed` оставляет в запросе только локальный `calculate` и MCP-инструмент `read_text_file` и печатает тело запроса к модели (без ключа и заголовков).

На странице http://127.0.0.1:8765/ день 16 подключает тот же сервер. Если `mcp` или `npx` не найдены, страница не падает, а показывает, чего не хватает.

## Результаты

Модель deepseek-flash. MCP-соединение установилось, сервер вернул 16 инструментов: `read_file`, `read_text_file`, `read_media_file`, `read_multiple_files`, `write_file`, `append_file`, `edit_file`, `create_directory`, `list_directory`, `list_directory_with_sizes`, `directory_tree`, `move_file`, `copy_file`, `search_files`, `get_file_info`, `list_allowed_directories`.

### Задача только через MCP

«Какие файлы в песочнице и что написано в notes.txt?»

| Шаг | Источник | Вызов | Результат |
| --- | --- | --- | --- |
| 1 | MCP | `list_allowed_directories` | путь песочницы |
| 1 | MCP | `list_directory` | notes.txt, order.txt |
| 2 | MCP | `read_text_file` для notes.txt | проект «оплата заказов», ответственный Максим, пометка что файл из MCP |
| 2 | MCP | `read_text_file` для order.txt | позиции 17, цена 23, доставка 8 |

Ответ модели повторил оба файла и содержимое `notes.txt` слово в слово. Все вызовы — инструменты, которые мы не писали.

### Смешанный набор

В запрос к модели одновременно попали один локальный инструмент дня 6 (`calculate`) и один MCP (`read_text_file`). Задача: прочитать `order.txt` и посчитать итог (количество × цена + доставка).

| Шаг | Источник | Вызов | Результат |
| --- | --- | --- | --- |
| 1 | MCP | `read_text_file(.../order.txt)` | 17, 23, 8 |
| 2 | local | `calculate((17 * 23) + 8)` | 399 |
| 3 | — | ответ текстом | «Итог заказа: 399» |

Оба инструмента понадобились, итог верный. В теле первого запроса (оно лежит в `runs.json` и печатается проверкой) нет ключа и заголовков. В массиве `tools` две одинаковые по форме схемы `function`: `calculate` и `read_text_file`. Различие «локальный / MCP» в этом JSON не размечено — его знает только наш реестр `sources`.

## Ответы на вопросы

### Как модель различает локальный инструмент и MCP-инструмент?

Никак. В запросе оба выглядят одинаково: объект `{ "type": "function", "function": { "name", "description", "parameters" } }`. Модель выбирает имя и аргументы. Кто исполнитель, решает наш диспетчер: в реестре у `calculate` стоит `local` — вызывается функция дня 6, у `read_text_file` стоит `mcp` — вызов уходит в `Client.call_tool`. В трассировке мы подписываем источник, чтобы это было видно в отчёте, но до модели эта подпись не доезжает как отдельное поле схемы.

### Что изменилось в коде при переходе на MCP?

Цикл агента тот же, что в дне 6. Добавились четыре вещи. Первая — установка соединения: запуск готового сервера и `list_tools`. Вторая — перевод схем MCP (`inputSchema`) в формат `tools[]`, который ждёт DeepSeek. Третья — диспетчер по реестру источников вместо одного словаря локальных функций. Четвёртая — печать тела запроса к модели без ключа. Локальный `calculate` не переписывался.

### Зачем тогда нужен MCP?

Чтобы не писать каждый инструмент самим и не привязывать агента к одной библиотеке. Сервер файловой системы, git или браузера говорит на одном протоколе, отдаёт список инструментов и выполняет вызов. Агенту достаточно уметь подключиться и вызвать инструмент по имени. Сервер можно заменить, цикл агента остаётся тем же. В этом дне агент прочитал файлы инструментом, которого в репозитории нет: его дал публичный `@modelcontextprotocol/server-filesystem`.

## Что нашлось по ходу

В смешанной задаче модель не стала перечислять каталог и сразу прочитала `order.txt` по пути из системного промпта. В задаче «только MCP» она сначала спросила у сервера список разрешённых папок.

Итог заказа — 399, не 391: 17 × 23 = 391, плюс доставка 8.

Первый запуск `npx -y` может занять время и требует сети. Если пакета `mcp` или `npx` нет, агент и страница не падают молча, а объясняют, что поставить. Файловый сервер видит только папку `sandbox`, пути снаружи он отвергнет.

Запуск:

```powershell
pip install mcp
python -m unittest test_mcp.py
python check_mcp.py
python agent.py --mixed Прочитай order.txt и посчитай итог
```
