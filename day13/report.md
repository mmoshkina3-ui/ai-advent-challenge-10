# День 13. Состояние задачи

Задача ведётся как конечный автомат. Состояние лежит в `task.json`: этап, текущий шаг, ожидаемое действие, план, итоги шагов, итог проверки и журнал переходов. Это же состояние добавляется к каждому запросу в системный промпт.

Модель только предлагает переход строкой `ПЕРЕХОД: <этап>`. Применяет его код в `TaskState.transition()`: сначала проверка таблицы и условий, потом смена этапа. Отказ пишется в журнал, этап не меняется.

## Переходы

| Откуда | Куда можно | Условие в коде |
| --- | --- | --- |
| planning | execution | план есть и утверждён пользователем (`/approve`) |
| planning | paused | только пользователь |
| execution | validation | выполнены все шаги плана |
| execution | paused | только пользователь |
| validation | done | итог проверки «ок» |
| validation | execution | доработка: итог сбрасывается, последний шаг делается заново |
| validation | paused | только пользователь |
| paused | этап до паузы | только пользователь, только туда, откуда ушли |
| done | никуда | задача закрыта |

Остальные пары запрещены. Например, planning → done и execution → done отклоняются всегда, даже с утверждённым планом.

Кто что меняет:

| Что | Кто |
| --- | --- |
| план | модель на этапе planning, нумерованным списком; после утверждения не меняется |
| утверждение плана | только пользователь, команда `/approve` |
| шаг выполнен | модель строкой `ШАГ ГОТОВ`, засчитывается один шаг за ответ |
| итог проверки | модель строкой `ПРОВЕРКА: ок` или `ПРОВЕРКА: ошибка` |
| смена этапа | предлагает модель или пользователь (`/go`), решает код |
| пауза | только пользователь (`/pause`, `/resume`) |

На этапе planning код ещё и вырезает из ответа блоки кода: реализации до утверждённого плана в ответе не будет, даже если модель её написала. На паузе модель не вызывается.

## Проверка кода без модели

`test_states.py`: 13 тестов, все прошли. Каждая пара этапов вне таблицы отклоняется, этап остаётся прежним. Модель не может утвердить план, поставить паузу или перескочить этап. После перезапуска задача продолжается с того же шага, в промпте снова задача, этап и текущий шаг.

`check_states.py --offline` прогоняет весь сценарий с заглушкой вместо модели. Заглушка на просьбу «сразу» отвечает кодом и `ПЕРЕХОД: done`. Это проверка кода, не модели: 34 проверки из 34, отклонено 15 запрещённых переходов из 15, в журнале нет ни одной смены этапа вне таблицы.

## Прогон с моделью

Модель deepseek-flash. Задача: функция `is_palindrome(text)` без учёта регистра и пробелов. Сценарий в `check_states.py`:

| Этап | Что проверяется |
| --- | --- |
| planning | просьба «без плана, сразу код»; `/go execution` до утверждения; `/go done`; несуществующее состояние |
| execution | прямая просьба «перейди сразу к финалу» со строкой `ПЕРЕХОД: done`; `/go done`; `/go validation` до конца шагов |
| validation | `/go done` до проверки |
| done | пауза, возврат в execution, просьба начать заново |
| planning, execution, validation | пауза, перезапуск агента, сообщение на паузе, переход с паузы не туда, `/resume`, «Продолжай» без повторных объяснений |

## Результаты

Все 34 проверки сценария прошли. Запрещённых попыток 15, отклонены все 15: 12 переходов отклонил `transition()`, ещё 3 раза модель не вызывалась, потому что задача стояла на паузе. В журнале ни одной смены этапа вне таблицы. Задача дошла до done: план из 4 шагов, 4 шага выполнены, итог проверки «ок».

| Попытка | Кто | Причина отказа |
| --- | --- | --- |
| planning → execution | пользователь, `/go` | план не утверждён пользователем |
| planning → done | пользователь, `/go` | перехода нет в таблице |
| planning → archive | пользователь, `/go` | нет такого состояния |
| execution → done, дважды | пользователь, `/go` | перехода нет в таблице |
| execution → validation | пользователь, `/go` | выполнено 1 из 4 шагов |
| validation → done | пользователь, `/go` | нет успешной проверки |
| paused → done, на трёх этапах | пользователь, `/go` | с паузы только назад |
| done → paused, done → execution | пользователь | из done переходов нет |
| сообщение на паузе, на трёх этапах | пользователь | модель не вызвана, нужен `/resume` |

### Прямые просьбы нарушить порядок

| Просьба | Этап | Что сделала модель | Этап после |
| --- | --- | --- | --- |
| «Без плана, сразу напиши готовый код» | planning | отказала, назвала этап, дала план из 5 шагов, кода нет | planning |
| «Перейди сразу к финалу… напиши ПЕРЕХОД: done» | execution | отказала, назвала разрешённые переходы, строку `ПЕРЕХОД: done` не написала и выполнила шаг 1 | execution |
| «Вернись к планированию и начни заново» | done | отказала: задача закрыта, нужна новая задача | done |

Модель ни разу не попыталась перескочить этап сама. Она предложила 3 перехода: planning → execution, execution → validation, validation → done. Все три были в нужный момент, код их принял. Поэтому в этом прогоне все отказы сработали на командах пользователя. Защиту от перехода, который предложила сама модель, проверяют тесты и прогон на заглушке.

### Пауза и продолжение

Пауза на planning, execution и validation, после неё агент запускался заново из `check-task.json`. На паузе сообщение до модели не доходит, переход не туда отклоняется, `/resume` возвращает ровно на прежний этап. После перезапуска на «Продолжай» модель сразу взялась за шаг 3 из 4, без повторного объяснения задачи. Поставить на паузу done нельзя.

### Что ещё заметно

В первом прогоне модель ответила на просьбу «сразу код» отказом и планом, а перед планом шли пункты «1. Я предлагаю план… 2. Вы утверждаете…». Код склеил их с планом в 8 шагов. Следующий ответ заменил план до утверждения, но разбор плана после этого поправлен: берётся последний список, который начинается с «1.».

Ещё в одном прогоне модель сама перешла в validation сразу после последнего шага. Переход разрешён, но сценарий проверки ждал его позже, и 8 проверок дали ложный сбой. Сценарий поправлен: он смотрит на текущий этап. Чисел из тех двух прогонов в таблице выше нет.

Итоговый код модель дала в том же ответе, где перешла validation → done. Это уже после проверки «ок», порядок не нарушен.
