# День 18. Планировщик и фоновые задачи

В приложении появился планировщик: фоновый цикл, который сам, без участия человека, по расписанию вызывает инструменты своего MCP-сервера. Источник данных локальный — учебная «очередь событий». Значения меняются от тика к тику по простой формуле, поэтому в сводке есть что складывать, и прогон не зависит от внешнего API и лимитов. Рядом снимается rss текущего процесса — живой, но не обязательный для агрегации показатель.

Клиент тот же, что в днях 16–17: соединение по stdio, `list_tools`, перевод схем, вызов `Client.call_tool`. Сервер свой, запускается тем же интерпретатором: `sys.executable day18/server.py`. Планировщик не вызывает функции Python хранилища напрямую: и сбор, и запись, и чтение периода идут только через MCP. Хранилище — SQLite, путь задаётся переменной `METRICS_DB` или флагом `--db`. Файл базы в git не попадает.

## Инструменты и расписание

Три инструмента регистрируются декоратором `@server.tool`. Параметры — аннотации типов и `pydantic.Field(description=...)`. Из них SDK собирает JSON Schema, которую клиент получает в `tools/list`.

| Инструмент | Параметры | Что делает |
| --- | --- | --- |
| `collect_metrics` | нет | Снимает текущий снимок: номер тика, время, число событий, задержку, ошибки, rss. В хранилище ничего не пишет. |
| `save_sample` | обязательные `tick`, `collected_at`, `events`, `latency_ms`; необязательные `errors`, `rss_kb`, `source` | Сохраняет снимок в SQLite и возвращает id и сколько всего записей накопилось. |
| `read_period` | необязательные `since`, `until` (ISO) | Возвращает все снимки за период и сводку по ним. Без границ — всё накопленное. |

Сводка считается по всем запускам периода, а не по последнему: число запусков, сумма событий, события последнего запуска отдельно, min/max/avg задержки, сумма ошибок, первый и последний момент, список тиков. Для четырёх тиков события идут как 3, 5, 7, 9: сумма 24, в последнем запуске 9 — это разные числа, и по ним видно, что отчёт не из одного снимка.

Планировщик (`scheduler.py`) в цикле, раз в `interval` секунд, вызывает `collect_metrics`, затем `save_sample`. После заданного числа сборов сам вызывает `read_period` и отдаёт сводку. Интервал, число сборов и путь к базе задаются флагами `--interval`, `--runs`, `--db` или переменными `SCHEDULER_INTERVAL`, `SCHEDULER_RUNS`, `METRICS_DB`. Для демо и прогона по умолчанию — 4 сбора каждую секунду: несколько запусков успевают накопиться без участия человека. Агент на DeepSeek может снять снимок вручную или прочитать сводку, но основное — автономный цикл.

## Как запустить

Нужны Python 3 и пакет `mcp`. Внешний API для планировщика не нужен, ключ модели — только для агента:

```powershell
pip install -U "mcp>=2"
# или: pip install -r day18/requirements.txt
```

Ключ — в окружении `DEEPSEEK_API_KEY` или в `day02/.env` / `day18/.env`. Проверка без модели:

```powershell
cd day18
python -m pytest test_scheduler.py
# или: python -m unittest test_scheduler.py
```

Автономный цикл и прогон с моделью:

```powershell
python scheduler.py --interval 1 --runs 4 --db metrics.db
python check_scheduler.py
python agent.py Покажи сводку за период и скажи, это сумма всех запусков или только последнего.
```

На странице http://127.0.0.1:8765/ день 18 поднимает тот же сервер и умеет запустить расписание кнопкой. Если пакета `mcp` нет, страница не падает, а показывает, чего не хватает. Сервер стартует тем же `python`, которым запущена страница.

## Результаты

Юнит-тесты: 17 из 17. Часть ходит в SQLite напрямую и проверяет накопление и то, что сумма событий не равна последнему запуску. Часть подменяет `call_tool` и проверяет, что планировщик вызывает только три MCP-инструмента, в нужном порядке. Живые тесты поднимают сервер по stdio, делают четыре сбора с коротким интервалом без участия человека и читают период ещё раз: в базе четыре снимка, сводка по всем.

Прогон с настоящей моделью `deepseek-flash`. MCP-соединение установилось, сервер назвался `metrics-scheduler` и вернул три инструмента. В схеме `save_sample` обязательны `tick`, `collected_at`, `events`, `latency_ms`. Планировщик без участия человека снял четыре снимка, по одному в секунду (время — Europe/Moscow, UTC+3):

| Запуск | Время | tick | events | latency_ms | errors | Всего в базе |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 27 ноября 2026, 09:46:28 | 1 | 3 | 120 | 0 | 1 |
| 2 | 27 ноября 2026, 09:46:29 | 2 | 5 | 105 | 0 | 2 |
| 3 | 27 ноября 2026, 09:46:30 | 3 | 7 | 90 | 1 | 3 |
| 4 | 27 ноября 2026, 09:46:31 | 4 | 9 | 75 | 0 | 4 |

Счётчик в базе после каждого запуска рос: 1, 2, 3, 4 — данные накапливаются, предыдущие снимки не затираются. Сводка за период: запусков 4, сумма событий 24, в последнем запуске 9, latency min/avg/max 75 / 97.5 / 120, ошибок всего 1 (тик 3). Сумма 24 не равна 9, это сумма всех четырёх запусков.

### Сводка глазами модели

«По сводке за период: сколько было запусков, какая сумма событий по всем запускам и сколько событий в последнем запуске? Это сумма всех запусков или только последнего?»

| Шаг | Источник | Вызов | Результат |
| --- | --- | --- | --- |
| 1 | MCP | `read_period({})` | 4 снимка и сводка: `events_total` 24, `events_last` 9 |
| 2 | — | ответ текстом | 4 запуска, сумма 24 (3+5+7+9), в последнем 9; явно сказано, что это сумма всех запусков |

Модель сама выбрала `read_period` без границ периода. В ответе есть все три числа и пояснение, что 24 — сумма всех запусков, а не только последнего, со ссылкой на `uses_all_runs`. Выдуманных цифр не было.

Тела запросов к модели (без ключа и заголовков) лежат в `runs.json`.

## Ограничения

Источник метрик учебный: события и задержка считаются от номера тика, а не снимаются с настоящей очереди или внешнего сервиса. Так проще показать накопление и не упереться в лимиты API. rss процесса живой, но от запуска к запуску может почти не меняться, поэтому в сводке на него нельзя опираться как на главное доказательство.

Интервал по умолчанию короткий (1 секунда), чтобы демо успело накопить несколько запусков. Для настоящей периодической задачи его нужно увеличить; сам цикл при этом тот же. Планировщик живёт, пока жив процесс приложения: отдельного системного сервиса (cron, systemd) нет.

`read_period` сравнивает границы `since`/`until` как строки ISO. Это работает для одного и того же смещения и одинаковой точности, как в этом дне, но это не полноценное сравнение меток времени.

Модель могла бы ответить «из головы» и не вызвать инструмент. В этом прогоне она вызвала `read_period`; защита от выдумки — промпт и проверка факта вызова, а не запрет в коде отвечать без инструмента.
