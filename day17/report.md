# День 17. Первый инструмент MCP

В этот раз MCP-сервер свой, а не готовый как в дне 16. Он написан на Python-пакете `mcp` (`MCPServer`, в версии 1.x тот же код поднимается через `FastMCP`) и запускается по stdio тем же интерпретатором, что и агент: `sys.executable day17/server.py`. Node.js и `npx` не нужны.

Сервер не хранит заказы у себя в памяти инструментов. При старте он поднимает маленький локальный HTTP API трекера (`tracker_api.py`, стандартный `http.server` на `127.0.0.1` и свободном порту) и вызывает его через `urllib`. В каталоге три заказа: ORD-1001 у Максима, статус «оплачен», сумма 399 (17×23+8); ORD-1002 «в доставке»; ORD-1003 «отменён». Внешние аккаунты и ключи API не нужны, сервер работает и без сети, кроме самого вызова модели.

Клиент и диспетчер те же, что в дне 16: соединение, `list_tools`, перевод схем в формат запроса к модели, вызов `Client.call_tool`, возврат результата в диалог. Изменилась только команда запуска сервера.

## Регистрация, схема и результат

Два инструмента регистрируются декоратором `@server.tool` с именем и текстовым описанием. Входные параметры — аннотации типов и `pydantic.Field(description=...)`. Из них SDK сам собирает JSON Schema, которую клиент получает в `tools/list`.

| Инструмент | Параметры | Что возвращает |
| --- | --- | --- |
| `get_order` | обязательный `order_id` (строка): «Идентификатор заказа, например ORD-1001. Регистр не важен.» | JSON заказа: статус, покупатель, позиции, доставка, сумма |
| `list_orders` | необязательный `status` (строка или null): фильтр «оплачен», «в доставке», «отменён» | список заказов с идентификатором, покупателем, статусом и суммой |

Инструмент делает GET на `/orders/{id}` или `/orders?status=...` и отдаёт разобранный JSON как результат. Если заказа нет, API отвечает 404, а инструмент возвращает объект с `error: not_found` — это не падение протокола.

## Как запустить

Нужен Python 3 и пакет клиента:

```powershell
pip install -U "mcp>=2"
# или: pip install -r day17/requirements.txt
```

Ключ модели — в окружении `DEEPSEEK_API_KEY` или в `day02/.env` / `day17/.env`. Проверка без модели:

```powershell
cd day17
python -m unittest test_tracker.py
```

Прямой вызов и прогон с моделью:

```powershell
python check_tracker.py
python agent.py Какой статус и сумма у заказа ORD-1001?
```

На странице http://127.0.0.1:8765/ день 17 поднимает тот же сервер. Если пакета `mcp` нет, страница не падает, а показывает, чего не хватает. Сервер стартует тем же `python`, которым запущена страница.

## Результаты

Юнит-тесты: 16 из 16. Среди них — HTTP API, `tools/list` со схемами и описаниями параметров, прямой вызов `get_order` и `list_orders`, диспетчер агента на подменённой модели.

Прогон с настоящей моделью `deepseek-flash`. MCP-соединение установилось, сервер назвался `order-tracker` и вернул два инструмента. В схеме `get_order` параметр `order_id` обязательный, в описании есть пример ORD-1001. Прямой вызов `get_order({"order_id": "ORD-1001"})` вернул статус «оплачен» и сумму 399.

Задача модели: «Какой статус у заказа ORD-1001 и какая у него сумма? Не выдумывай данные, возьми их инструментом трекера.»

| Шаг | Источник | Вызов | Результат |
| --- | --- | --- | --- |
| 1 | MCP | `get_order({"order_id": "ORD-1001"})` | статус «оплачен», сумма 399, покупатель Максим |
| 2 | — | ответ текстом | «Статус: оплачен. Сумма: 399 RUB» |

Модель сама выбрала наш инструмент и передала верный идентификатор. В ответе она опиралась на результат: назвала статус и сумму, плюс покупателя, состав и дату из того же JSON. Тело запроса к модели (без ключа и заголовков) лежит в `runs.json`.

## Ограничения

Это не живой Яндекс.Трекер и не внешняя CRM, а свой mock HTTP API с тремя заранее заданными заказами. Обёртка настоящая: инструмент ходит по HTTP, а не читает словарь напрямую, но данные всё равно локальные и статичные.

Код ловит устаревшую версию пакета `mcp` через запасной импорт `FastMCP`, но проверка и страница рассчитаны на `mcp` 2.x. Если пакета нет, сервер не стартует — это видно в сообщении, а не в падении страницы.

Модель могла бы ответить «из головы» и не вызвать инструмент. В этом прогоне она вызвала его; защита от выдумки — промпт и проверка факта вызова, а не запрет в коде отвечать без инструмента.

Фильтр `list_orders` сравнивает статус точно, как в каталоге: «оплачен», а не «paid» или «оплаченный». Несуществующий заказ не падает, но и не предлагает похожий идентификатор в ответе модели — только в JSON ошибки.
