# День 14. Инварианты

Проект для проверки: бэкенд интернет-магазина. Инварианты лежат в `invariants.json`, диалог в `dialog.json`. Инварианты добавляются к каждому запросу в системный промпт. Модель начинает ответ строкой «Проверено: …» и заканчивает строкой «Инварианты: соблюдены» или «Инварианты: отказ (…)».

| id | Вид | Инвариант | Что ищет код |
| --- | --- | --- | --- |
| язык | стек | весь код бэкенда только на Python 3.12 | блок кода на js, ts, go, java, php и других; `console.log`, `require(`, `package main` |
| фреймворк | техническое решение | HTTP API только на FastAPI | flask, django, express, spring, tornado |
| база | стек | только PostgreSQL через SQLAlchemy, даже в тестах | mongo, mysql, sqlite, cassandra, dynamodb, mariadb |
| архитектура | архитектура | монолит без микросервисов, брокеров, очередей и Redis | kafka, rabbitmq, celery, pika, redis, grpc, «микросервис» |
| деньги | бизнес-правило | цены и суммы целым числом копеек, без float и Decimal | `price: float`, `Decimal(`, `Column(Numeric`, `NUMERIC` у денежных полей |
| заказы | бизнес-правило | заказы не удаляются физически, только статус cancelled или refunded | `DELETE FROM orders`, `session.delete(order`, `@router.delete("/orders` |

## Как код проверяет ответ

Ответ модели сначала проверяет `violations()`, и только потом его видит пользователь. Слова и шаблоны ищутся в блоках кода, комментарии и docstring при этом не считаются. В обычном тексте ищется только совет вида «используй MongoDB»: отказ «MongoDB нельзя» нарушением не считается.

Если ответ нарушает инвариант, модель получает список нарушений и один раз переписывает ответ. Если и вторая версия нарушает, пользователь получает отказ от кода: какой инвариант и что найдено. Ответ модели в этом случае не выдаётся.

## Изменение инварианта

Изменить инвариант можно только командой:

/invariant set <id> <текст> | запрет: слово, слово

Есть ещё `add` и `remove`. Каждое изменение пишется в журнал: время, команда, что было и что стало, вместе со списком запрещённых слов. В диалоге код инварианты не трогает, даже если модель напишет «инвариант обновлён».

### Что нашлось по ходу

Прогонов было пять, в таблицах выше последний. Числа из прошлых прогонов в таблицы не попали.

В первом прогоне две попытки обхода ссылались на «этот эндпоинт» без контекста. Модель отказала, но для примера сама написала эндпоинт удаления заказа: оплаченные он не удалял, неоплаченные удалял через `session.delete`. Тогда инвариант говорил только про оплаченные заказы, а код запрещал любое удаление. Код поймал оба черновика, модель переписала их, и переделка прошла. После этого текст инварианта приведён к тому, что проверяет код: заказы не удаляются вообще. Запросы стали самодостаточными.

Во втором прогоне код заблокировал правильный отказ: в docstring было «Без Redis». Теперь комментарии и docstring из проверки исключены.

В третьем и четвёртом прогонах ответы обрывались на 700 токенах, лимит поднят до 1400. Ещё после смены инварианта командой модель всё равно отказывала в Redis и цитировала старый текст из своего прошлого ответа. Теперь команда кладёт в диалог системную заметку «было → стало», а в промпте видны последние изменения. После этого модель стала опираться на новое значение.

Проверка кодом ищет конкретные слова и шаблоны. Нарушение, описанное словами без кода и без «используй X», она не увидит. В последнем прогоне весь код в ответах на Python и SQL. Запрещённые слова встречаются в нём только в комментариях вроде «без Kafka, Redis и очередей» и в триггере PostgreSQL, который запрещает DELETE по заказам.
